# Обновление: тот же файл с именем по ФИО и дате — 20.10.2026

По последнему уточнению выбранный XLSX обновляется и переименовывается в **`ФИО DD.MM.YYYY.xlsx`**. Папка сохраняется, постоянная копия не создаётся. При отсутствии имени используется `Договор DD.MM.YYYY.xlsx`; коллизии получают `(2)`, `(3)` без перезаписи другого файла. Повторное сохранение не нумерует текущий файл заново. Дата берётся в момент сохранения.

GUI показывает новое имя в единственной сводке, а после успеха переключает путь текущего документа на новое имя. Проверенный временный XLSX готовится заранее; затем исходный файл перемещается без перезаписи занятого имени и заменяется проверенным результатом. При ошибке записи выполняется возврат прежнего имени. Если возврат тоже заблокирован, программа сообщает путь, где остался документ. Переименование и замена — две файловые операции; единая атомарность обеих не заявляется.

Запуск актуальной Windows x64 CPU-поставки: **`dist-renamed/DocumentExcel/DocumentExcel.cmd`**. `Launch.cmd` использует её через `current-build.txt`. Ниже — история предыдущих вариантов поведения.

# Обновление: сохранение в выбранный файл — 20.10.2026

По последнему требованию пользователя основной GUI обновляет выбранный XLSX **на месте**, сохраняя имя и папку. В итоговой сводке нет выбора нового имени/папки. `WorkbookService.update_existing()` явно разрешает замену выбранного источника; обычный сервисный `write()` сохраняет прежнее поведение экспорта отдельного файла для совместимости legacy-вызовов.

Изменения сначала записываются во временный файл в той же папке. После проверки структуры, значений, изображений и неизменности выбранного источника временный результат публикуется через `os.replace()`. При ошибках записи/проверки/замены прежний документ не изменяется. Read-only файл не заменяется; при блокировке Excel нужно закрыть документ. Для обновления источника нет запасного способа с частичной записью поверх него. Прежняя политика отсутствующих данных/фото и защита формул сохраняются.

Ниже — описание предыдущего выпуска; пункты об обязательной отдельной копии и новом имени относятся к прежнему поведению и legacy-экспорту.

# Обновление архитектуры — 20.10.2026

Основной режим теперь `BEST_EFFORT_UPDATE`, видимый процесс: Загрузка → Проверка → Готово. Пропуски отделены от препятствий безопасности; обработка прежних данных и фото задаётся одним решением в итоговой сводке. Источник остаётся неизменным, генератор договора не вызывается. # Архитектура

## Обновление существующего договора

Основной GUI использует `WorkflowMode.EXISTING_CONTRACT`. Проверенная карта
и выбранный исходник принадлежат ClientCase; смена договора сохраняет OCR,
но сбрасывает экспортное подтверждение. В этом режиме WorkbookService
обходит генератор инструментов и финансовых полей, применяет отдельный
allowlist и повторно строит план перед записью. Очистка старых паспортных
значений, сохранение контактов и замена фото требуют явного решения.
PackageEditor удаляет освобождённые персональные shared strings, сохраняя
общие используемые индексы. PersonNameFormatter и ContractFilenameGenerator
отделены от распознавания и получают локальную дату при сохранении.
[Аудит, состояние и ограничения](docs/CUSTOMER_WORKFLOW.md).

## Актуальность OCR и разрешение полей

`ClientCase` хранит текущие данные, свидетельства, отдельные официальные формы имени, историю `OcrRun`, проверку принадлежности сторон и диагностические события. `application/ocr_state.py` создаёт UUID запуска и снимки источников с фактическими SHA256. Перед публикацией проверяются клиент, последний запуск, байты, поворот, роль, выбранная версия изображения и ручной тип документа. Результат разрешается на отдельной копии и публикуется одним обновлением в GUI-потоке. Отменённый, чужой или устаревший результат не меняет реквизиты.

Новый запуск заменяет вклад прочитанных источников, включая исчезнувшие поля; свидетельства других фотографий и ручные значения сохраняются. Повтор одного поля ограничивает область обновления. Производное ФИО пересобирается только из текущих компонентов и ссылается только на использованные варианты; переключение фотографии не запускает это разрешение. Ручной адрес прежнего формата восстанавливает явное происхождение по статусу MANUALLY_ENTERED.

`domain/resolution.py` не зависит от Qt, OCR или инфраструктуры. `FieldResolver` проверяет семантику, сторону и область, отсекает недопустимые кандидаты до сравнения уверенности, сохраняет ручное значение и отмечает расхождение с новым OCR. Функция `infrastructure.extraction.apply_candidates` сохраняет прежний интерфейс вызова. Специализированные форматы выделены в `infrastructure/field_extractors.py`; строгий TD1 остаётся в `mrz.py`.

Если реквизиты не связывают основные фотографии, результат ожидает подтверждения принадлежности в `pending_identity`, без слияния ClientData. До проверки экспорт заблокирован. После изменения файлов подтверждение недействительно. Диагностика хранит в памяти ограниченный список событий и метаданные блоков; полные реквизиты скрыты по умолчанию. Подробный аудит и обезличенная проверка реальных фото — [OCR_STATE_AUDIT.md](docs/OCR_STATE_AUDIT.md).

Уточнение официальных реквизитов пластиковой карты вынесено в `infrastructure/region_ocr.py`: `RegionBasedOCR`, `FieldRegion`, `DocumentNumberExtractor`. Оно сохраняет обычный OCR как независимый источник, ограничивает число областей/проходов и возвращает стандартные FieldCandidate с исходными bbox. Имена полей Excel сохраняются; вычисляемый `ClientData.document_number` объединяет тип/цифры без второй копии данных. Повтор поля использует выбранную версию снимка и идентификатор клиента, сохраняя ручные правки. Подробности — `docs/ID_FIELDS_FIX.md`.

## Пластиковая ID-карта и источники MRZ

DocumentType расширен KG_PHYSICAL_ID/KG_DIGITAL_ID, старый kg_id сохранён для совместимости. DocumentTypeClassifier использует несколько текстовых/структурных признаков и геометрию, DocumentSideClassifier различает профили сторон. KyrgyzPhysicalIDProfile, KyrgyzDigitalIDProfile и UnknownDocumentProfile расширяют прежний DocumentProfile; политика регистрации, языки, области и MRZ-стратегия отделены от Excel-профиля. При позднем определении профиля по второй стороне RecognitionService один раз перечитывает ранее обработанные изображения. Ручной выбор типа имеет приоритет. Назначенная ADDITIONAL сохраняется; расхождение выбранных FRONT/BACK создаёт предложение с явным подтверждением.

physical_id.py находит четырёхугольник, выпрямляет карточку, поддерживает поворот и обратное преобразование bbox в систему исходного изображения. Нормализованные области профиля уточняются по найденным подписям и следующему полю. Двуязычные строки разделяются по изображениям строк и читаются соответствующими языками. Тип/цифры номера при необходимости перечитываются отдельными областями; префикс не создаётся из цифрового OCR. Предложения crop для Excel по-прежнему требуют подтверждения через существующий PhotoEditor; OCR-преобразования не подменяют фотографии молча.

mrz.py реализует строгий TD1 и четыре проверки ICAO 9303. Распознавание нижней области отделено от обычного текста. Кандидаты из нескольких ограниченных проходов и оптического определения шевронов принимаются только после структурной и контрольной проверки. Цифра составного блока читается из пикселей. Никаких дополнений длины, подстановки вычисленной контрольной цифры или слепой замены O/0 и I/1 нет. Уточнение типов символов использует специальные OCR-алфавиты и геометрию, а не словарь фамилий. Поддержан стандартный длинный номер TD1; правило optional ПИН ограничено проверенным форматом КР.

FieldCandidate.source_method различает VISUAL_OCR/MRZ; FieldEvidence хранит ручное происхождение и статус подтверждения. MRZReport принадлежит ClientCase и source image id; строки/значения исключены из repr и не сериализуются в журнал. Отдельные официальные формы имени хранятся в ClientData, ручные правки согласуют форму и составное ФИО. Место рождения отделено от Address. При конфликте с MRZ новый вариант автоматически не выбирается; существующее ручное значение сохраняется. Даты MRZ получают столетие только из совпадающей полной визуальной даты.

После двух сторон физического профиля без кандидата регистрации используется NOT_PRESENT. Цифровой профиль сохраняет прежнее различение UNCERTAIN/NOT_RECOGNIZED. Отдельный документ или ручной адрес поступает в обычный Address и проходит требования шаблона. Удаление/пересъёмка фото удаляет связанные отчёты MRZ и производные формы имени. GUI показывает строки только в отдельном диалоге; постоянная форма содержит компактный итог и действие ввода прописки.

`ClientData` хранит строки и календарные даты; ПИН никогда не переводится в число. Регистрация и проживание независимы. `FieldCandidate` содержит исходный текст, нормализацию, координаты, идентификатор фото, метод, вариант подготовки и эвристическую уверенность. `FieldEvidence` различает OCR, ручные правки, конфликты и подтверждения. `ClientCase` группирует фото одного человека, `DocumentBatch` объединяет клиентов.

Изображения валидируются по размеру файла/числу пикселей, проходят EXIF-коррекцию. Оценка качества эвристическая. Auto консервативно находит карточку, включая почти квадратный мобильный макет, исключая отдельный QR. При неоднозначности остаётся оригинал. OCR выбирает обработанную область; полный оригинал доступен в просмотре. Perspective/deskew включаются явно. Координаты кадрирования, ROI и внутреннего увеличения Tesseract переводятся в оригинал; непроверенные геометрические преобразования не выдают ложных рамок. Исходники не меняются; просмотр хранит только текущее изображение.

Tesseract вызывается через `pytesseract.image_to_data`, слова объединяются в строки по bounding boxes. Извлечение использует многоязычные метки, пространственную близость, нормализацию, форматные проверки и сравнение кандидатов. Телефоны и коммерческие поля не извлекаются. Классификация требует нескольких признаков; неопределённый тип выбирает пользователь. Повторный OCR сохраняет ручные значения. Конфликты разрешаются отдельно от общего подтверждения.

Отсутствие распознанного адреса даёт UNCERTAIN/NOT_RECOGNIZED. Только пользователь указывает NOT_PRESENT. FOUND/PARTIALLY_FOUND не снимают требование проверки регистрации. Подтверждение связано с SHA256 данных, коммерческих полей, фото и статусов. Экспорт связывает dry-run также с профилем и содержимым исходного XLSX.

Qt использует сгруппированные ReviewField, QGraphicsView, QThreadPool/QRunnable и queued signals. components.py задаёт общие элементы, theme.py — токены, workflow_view.py — пять этапов и адаптивную компоновку. MainWindow управляет состоянием, QUndoStack и lifecycle; CaseActions и ExcelActions координируют действия. QAbstractTableModel сохранён как адаптер данных и совместимости, скрытая таблица не занимает экран. Ошибочные даты дополнительно хранятся как текст в памяти текущей записи. Worker получает снимки и возвращает результаты в GUI-поток через QObject-получателей, уничтожаемых вместе с окном. Из-за глобального executable в pytesseract вызовы сериализованы. На изображение выполняется основной и не более одного альтернативного PSM-прохода; выбирается результат по пригодным полям и покрытию меток.

Если подписанный номер начинается с неоднозначных 10/1D и серия не распознана, Identifier OCR делает один дополнительный ограниченный проход только по области номера: English PSM 7, без словарей, увеличение 3× и белая рамка. Регулярное выражение лишь выбирает область для повторного чтения. Буквы ID должны появиться в новом OCR, а вся цифровая часть — совпасть с суффиксом первого прохода; иначе исходный кандидат сохраняется. Принятые тип и номер остаются REVIEW с исходными image_id/bbox/стороной. Ручные значения защищает apply_candidates. Полный raw OCR и уточнённые кандидаты хранятся только в памяти; ни один проход не меняет общие языки и PSM движка. Дополнительное чтение номера не заменяет остальные поля выбранного основного прохода.

Отмена кооперативная до/после прохода; текущий проход ограничен timeout. Закрытие ждёт завершения через event loop. Короткая атомарная запись Excel доводится до конца, чтобы не сообщать отмену после сохранения. Отмена задания очереди OCR не применяет его частичные результаты.

ExcelDataAssembler формирует значения до записи. WorkbookService читает через openpyxl и проверяет mapping, формулы, объединения, защищённые листы, границы и особенности файла. PackageEditor меняет только запланированные ячейки и необходимую служебную XML-структуру исходного ZIP/XLSX. Остальные части копируются побайтно, без повторной сериализации рисунков, внешних ссылок и формул других листов. Устаревшая цепочка расчёта удаляется с её связью и описанием; Excel перестраивает её при пересчёте. Строки записываются inlineStr, даты — числами с форматами Excel. Пустые поля пропускаются по умолчанию. Для проверенной структуры lermontov применяется отдельная карта с шагом строк 2 и заводскими номерами в акте приёма. Дополнительные приложения копируются вместе с актами; квалифицированные ссылки формул переназначаются через токены, строковые литералы не изменяются. Логотипы копируются вместе с отношениями к исходным медиа. Временный результат открывается повторно, проверяются значения и неизменяемая часть книги. Исходник остаётся backup. Публикация через os.link отказывается заменять существующий файл.

Настройки и минимальная история сохраняются атомарно. Персональных черновиков нет. В журнал попадают только технические коды и типы ошибок. Runtime не использует сеть. Установка движка/зависимостей выполняется отдельными скриптами.

## Камера и фотографии договора

CameraService отделён от Qt-диалога и Excel. OpenCV выбран потому, что он уже входит в проект, а PySide6-Essentials не поставляет Qt Multimedia. Поиск устройств, настройка разрешений и чтение выполняются в фоновых потоках Python; QObject передаёт результаты сигналами в GUI. Windows использует DirectShow с fallback MSMF, Linux — V4L2. Проверяются реально выдаваемые размеры кадров; preview уменьшается, снимок копирует полный кадр. При смене формата очищаются старые кадры, несовпадение размера снимка не принимается. Все обычные пути выхода освобождают VideoCapture в finally. Закрытие диалога и главного окна ждёт освобождения через QTimer, без блокировки event loop.

DocumentCaptureController сохраняет неизменяемый оригинал отдельно от производной PNG и назначает FRONT/BACK конкретному ClientCase. SourceImage.selected_path выбирает производную только после подтверждения; digest защищает её от изменения перед экспортом. Оригинальные файлы не перезаписываются. Копирование включается существующей настройкой; постоянные папки разделяются по хэшу id клиента, временные принадлежат одному контроллеру и удаляются после завершения работников. Замена одной стороны сохраняет другую и сбрасывает связанные OCR/подтверждение. Перестановка сторон также требует повторной сверки. FieldCandidate.image_version различает координаты оригинала и подтверждённого crop при показе bbox и OCR выделенной области.

DocumentImageProcessor предлагает консервативную четырёхугольную перспективу либо прямоугольный crop, допускает ручное выделение, поворот и возврат к оригиналу. Оценки резкости, освещения и размера служат предупреждениями. CameraDialog последовательно принимает стороны; данные сохраняются контроллером до принятия кадра, ошибки сохранения оставляют снимок открытым. После завершения CaseActions запускает существующий OCR. PhotoReviewDialog переиспользует редактор для файлов. Закрытые диалоги удаляются через deleteLater, чтобы не удерживать полноразмерные массивы.

ExcelImageEmbedder строит XLImage/TwoCellAnchor/AnchorMarker через openpyxl, затем добавляет только необходимые drawing/media/relationships/content-types через существующий PackageEditor. Полная книга не пересохраняется openpyxl. SheetGeometry читает фактические ширины столбцов, высоты строк, скрытые размеры и объединения; ширины SpreadsheetML уже включают padding. MDW берётся из шрифта Normal, координаты переводятся в EMU. Contain с отступом 4 px центрирует FRONT в A1:E24 и BACK в F1:K24. Имена листов сопоставляются без учёта регистра и лишних пробелов, отсутствие листа блокирует экспорт.

План фотографий содержит входные SHA256, якоря, данные PNG и изменения рисунков. Метка рисунка включает хэш id клиента и сторону: повторный экспорт заменяет свои рисунки, чужая клиентская метка блокирует операцию. Неизвестные пересечения требуют отдельного явного согласия с превью; другие объекты внутри области блокируются. Рисунки вне областей сохраняются. При разрешённом исключении удаляются устаревшие собственные фото отсутствующих сторон. После записи проверяются число, имена, байты, внутренние отношения и точные якоря новых изображений. Существующие проверки ячеек, профиля, исходного SHA256 и атомарной публикации остаются обязательными.
