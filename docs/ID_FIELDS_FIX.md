# Орган выдачи и номер пластиковой ID-карты

Обновление 18 октября 2026. Сборка: `dist-id-fields/DocumentExcel`, запуск через `Launch.cmd`.

## Причины ошибок

Орган выдачи читался одним проходом из фиксированной области. Мелкие соседние подписи и обрезанные штрихи мешали Tesseract: ошибка буквы возникала при оптическом чтении, а не нормализации. Кроме того, строчные кириллические результаты отвергались проверкой только заглавных букв. Обязательный deskew короткой строки мог повернуть её по диагоналям букв и обрезать края.

Правильный номер присутствовал в общем OCR и проверенной MRZ, но поздний проход фиксированной области заменял правильный результат. Повтор номера под штрихкодом мог не иметь распознанной подписи.

## Исправления

`RegionBasedOCR` ищет область по словам подписи, строкам значения, относительному профилю и геометрии штрихкода. Шестизначная часть органа помогает найти фактическую строку, исключив соседние подписи. На поле оставляются максимум две области.

Сравниваются исходный crop, grayscale, CLAHE, adaptive threshold и увеличение 3×. Deskew номера выполняется отдельным дополнительным вариантом. Используются PSM 7/13, латиница с цифрами для номера и общий кириллический алфавит с цифрами для органа. Временная UTF-8-конфигурация удаляется после вызова. Регистр приводится к верхнему, буквы кодов не заменяются по словарю. Исходный текст кандидата остаётся в памяти.

`DocumentNumberExtractor` принимает ID и ровно семь прочитанных цифр данного профиля. Пробелы/регистр нормализуются. Похожий префикс или пропущенная буква согласуются только с другим буквальным чтением ID с тем же цифровым суффиксом. ПИН, неверная длина и O внутри цифровой части не превращаются в придуманный номер.

Правильные буквальные номера общего OCR сохраняются. FRONT, BACK и проверенная MRZ сопоставляются. Разные варианты дают CONFLICT, совпадение трёх источников — VALID с обязательной проверкой сотрудником. Ручные исправления защищены.

Полный `ClientData.document_number` вычисляется из существующих типа/номера, не создавая рассогласованной копии. ПИН — отдельный `personal_identifier`. Договор сохраняет тип в E19, цифровой номер в G19, орган в J19 и ПИН в C22; ведущие нули остаются строками.

## Проверка в интерфейсе

Меню поля показывает варианты с источниками «Лицевая сторона», «Оборотная сторона», «MRZ». Выбор автоматически выделяет исходную область. Одинаковые значения одного источника сгруппированы.

«Повторно распознать область поля» перечитывает выбранный участок органа/номера несколькими способами, сохраняя другие фото, MRZ и ручное значение. Для источника MRZ открывается её проверка с существующим повторным OCR. Ручное исправление остаётся в основном поле.

## Локальная проверка

На предоставленных фото орган совпал с контрольным значением; правильный номер найден у FRONT, BACK и MRZ. Некоторые альтернативные проходы читают другие цифры: CONFLICT сохранён для выбора по фотографии. Реальные реквизиты в проект не копировались.

Синтетические тесты проверяют Е/О и смешанные алфавиты, пропущенные префиксы, неверную длину, три источника, геометрию, отмену/ошибки OCR, контраст/блики/размытие, настоящий Tesseract для обоих кодов, Qt-повтор области, ручные правки, изоляцию клиентов и независимые ячейки Excel. Результаты — в `TEST_REPORT.md`.

`scripts/check_id_fields_private.py` читает контрольные значения из пользовательского текста только в память. Вывод содержит совпадения, статусы и геометрию; персональные значения не сохраняются в фикстурах или обычных журналах.
