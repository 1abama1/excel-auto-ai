# Обновление: тот же файл с именем по ФИО и дате — 20.10.2026

По последнему уточнению выбранный XLSX обновляется и переименовывается в **`ФИО DD.MM.YYYY.xlsx`**. Папка сохраняется, постоянная копия не создаётся. При отсутствии имени используется `Договор DD.MM.YYYY.xlsx`; коллизии получают `(2)`, `(3)` без перезаписи другого файла. Повторное сохранение не нумерует текущий файл заново. Дата берётся в момент сохранения.

GUI показывает новое имя в единственной сводке, а после успеха переключает путь текущего документа на новое имя. Проверенный временный XLSX готовится заранее; затем исходный файл перемещается без перезаписи занятого имени и заменяется проверенным результатом. При ошибке записи выполняется возврат прежнего имени. Если возврат тоже заблокирован, программа сообщает путь, где остался документ. Переименование и замена — две файловые операции; единая атомарность обеих не заявляется.

Запуск актуальной Windows x64 CPU-поставки: **`dist-renamed/DocumentExcel/DocumentExcel.cmd`**. `Launch.cmd` использует её через `current-build.txt`. Ниже — история предыдущих вариантов поведения.

# Обновление: сохранение в выбранный файл — 20.10.2026

По последнему требованию пользователя основной GUI обновляет выбранный XLSX **на месте**, сохраняя имя и папку. В итоговой сводке нет выбора нового имени/папки. `WorkbookService.update_existing()` явно разрешает замену выбранного источника; обычный сервисный `write()` сохраняет прежнее поведение экспорта отдельного файла для совместимости legacy-вызовов.

Изменения сначала записываются во временный файл в той же папке. После проверки структуры, значений, изображений и неизменности выбранного источника временный результат публикуется через `os.replace()`. При ошибках записи/проверки/замены прежний документ не изменяется. Read-only файл не заменяется; при блокировке Excel нужно закрыть документ. Для обновления источника нет запасного способа с частичной записью поверх него. Прежняя политика отсутствующих данных/фото и защита формул сохраняются.

Ниже — описание предыдущего выпуска; пункты об обязательной отдельной копии и новом имени относятся к прежнему поведению и legacy-экспорту.

# Best-effort обновление существующего XLSX

20.10.2026. Стандартный режим `ClientCase` и desktop-приложения — `WorkflowMode.BEST_EFFORT_UPDATE`. `TEMPLATE_GENERATION` и прежний строгий `EXISTING_CONTRACT` сохранены для явного сервисного/дополнительного использования.

## Валидация

`RecognitionWarnings` (`ValidationWarnings`) содержит найденные, отсутствующие и требующие проверки поля и информационные сообщения. Пропуски, неизвестный тип документа, неполное ФИО, ручной ввод и отсутствие сторон не блокируют экспорт. `ExportSafetyErrors` (`BlockingExportErrors`) проверяет выбранный договор, наличие карты и неразрешённое смешивание документов разных людей. `readiness()` в новом режиме возвращает только препятствия безопасности. Проверки самого XLSX остаются в `WorkbookService.plan()`/`write()`.

Невалидные, конфликтующие и служебные значения не записываются. Достоверные доступные значения записываются без отдельного подтверждения каждого поля. Отсутствующий или ошибочный реквизит требует предупреждения, а не обязательного ввода. Часть данных может оставаться «Проверьте»: это не утверждение о проверке человеком.

## Пропуски и прежний клиент

`MissingValuePolicy`: `LEAVE_EMPTY`, `PRESERVE_EXISTING`, `CLEAR_OLD_PERSONAL`. Пустая исходная ячейка остаётся пустой. Если есть старые значения/фото, требуется одно общее решение. `LEAVE_EMPTY` не разрешает незаметно оставить их.

Расхождение ФИО или идентификаторов считается возможной сменой клиента. Совпадающее начало неполного имени само по себе не доказывает смену. При смене пропущенные персональные поля очищаются; сохранить старые реквизиты нельзя. При неизвестной принадлежности пользователь выбирает сохранение для того же клиента или очистку для нового. Телефоны и адрес проживания относятся к клиенту; адрес объекта и коммерческие данные в обычном режиме не меняются.

Решение живёт в `ExportPlan`, применяется в единственной итоговой сводке и независимо воспроизводится перед записью. Подмена значений, диапазонов, изображений или добавление листов в план отклоняется. После сохранения `ClientCase` содержит политику, итоговый путь, обновлённые/пропущенные/очищенные/оставленные поля.

## Формулы

Пустой реквизит не разрешает удалить формулу. Прямая цепочка ссылок между разрешёнными персональными ячейками сохраняется. При изменении клиента старые кешированные результаты таких формул удаляются в пределах карты; текст формул остаётся прежним. Формула с литералом старого клиента, внешней зависимостью или циклом не считается безопасной для очистки и требует изменить профиль/исходник. Новое значение не может заменить защищённую формулу даже при разрешении, унаследованном из генератора шаблонов.

## Фотографии

Сохраняется существующий `ExcelImageEmbedder`, пропорции и области FRONT `A1:E24`, BACK `F1:K24` листа профиля. В новом режиме отсутствующая сторона допустима. Новая сторона заменяет прежнюю; отсутствующая сохраняется только согласно решению для того же клиента или очищается для нового. Сводка показывает прежние рисунки, чтобы проверить, что в разрешённых областях находятся паспортные фото. Посторонние рисунки вне областей сохраняются. Рисунки, пересекающие границы нескольких областей, и непонятные объекты требуют исправления исходника. Для неоднозначных/дублирующихся сторон новые фото пропускаются до уточнения роли.

## XLSX и публикация

Профиль известной структуры определяется автоматически; пользовательский профиль привязывается к структуре/содержимому и сохраняется в прежнем `TemplateRegistry`. Неизвестный файл не получает случайную карту. В обычном режиме не вызываются таблицы инструментов, расчёты и создание дополнительных листов.

Сохранены контроль хеша исходника, разрешённых ячеек, структуры, формул, ZIP-частей, атомарный временный файл в папке результата, повторное открытие и проверка значений. Публикация жёсткой ссылкой атомарна и не заменяет существующее имя. На файловой системе без ссылок используется эксклюзивная копия с проверкой хеша и очисткой при ошибке. Этот запасной способ **не атомарен**: другой процесс может видеть файл во время копирования. Перезапись существующего результата запрещена в обоих случаях. Если изменений вообще нет, сохраняется побайтовая копия исходника.

## UI и производительность

Видимые этапы: Загрузка → Проверка → Готово. OCR — промежуточное состояние. Боковая навигация скрыта; расширенные функции доступны из меню. Отсутствие общего номера на двух сторонах подтверждается в той же итоговой сводке; противоречащие номера/имена/даты между фотографиями сохраняют отдельную проверку принадлежности. Кнопка сохранения на проверке не зависит от числа паспортных полей. Имя, папка, фото и политика прежних данных объединены в `CopySaveDialog` без обязательных чекбоксов.

RapidOCR CPU остаётся основным по измерениям в [CPU_BENCHMARK](CPU_BENCHMARK.md). Модели и кеш существующей инфраструктуры не заменены; редактирование и просмотр фото не вызывают OCR. Запись, открытие XLSX и распознавание выполняются фоновыми workers. Сигналы редактирования подавляются при смене клиента и перерисовке формы, чтобы старый текст не попадал в новую запись.
