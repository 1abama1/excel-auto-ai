# PaddleOCR: производительность и полное ФИО

Исторический этап. Текущая CPU-поставка и новое сравнение PaddleOCR/RapidOCR:
[CPU benchmark](CPU_BENCHMARK.md). Активная сборка теперь `dist-cpu/DocumentExcel`.

Проверка от 19.10.2026. Windows x64, Python 3.12.13, PaddleOCR 3.7.0,
PaddlePaddle CPU 3.3.1, PaddleX 3.7.2. Intel Family 6 Model 165, 12 логических
процессоров; рабочее ограничение — 2 потока inference, один последовательный
процесс с моделями. GPU в этом CPU runtime не используется.

Новая автономная сборка: `dist-paddle-fast/DocumentExcel/DocumentExcel.cmd`.
`Launch.cmd` выбирает её через `current-build.txt`. Предыдущая сборка сохранена.

## Причины и исправления

1. Старый сценарий повторял полный OCR для document, contrast и physical-card,
   затем безусловно перечитывал поля. Новый сценарий сначала читает по одному
   выровненному цветному изображению каждой стороны, затем использует готовые
   блоки. Чтение областей запускается для отсутствующих/невалидных/слабых полей.
   Проверка 180° разрешена при неизвестной стороне и слабом результате;
   геометрическое исправление карты и ручной поворот сохранены.
2. В исходном основном OCR уже присутствовали полные фамилия и имя в двух
   формах. Последующие узкие кропы создавали обрезанные альтернативы, а их
   объединение делало правильные значения конфликтными. `FullNameExtractor`
   находит три подписанные группы FRONT, собирает соседние блоки по базовой
   линии и сохраняет отдельные кириллические и латинские формы.
3. Повтор имени использует полную ширину группы и учитывает вертикальные
   границы блока. Низкую строку можно увеличить перед recognition. Фрагменты
   не отбрасываются из-за длины или большого промежутка между словами.
   Слабое повторное чтение не заменяет уверенно прочитанное полное имя.
4. MRZ сначала читает три оригинальные строки и проверяет TD1. При успешной
   проверке дополнительные фильтры не запускаются. Резервные варианты
   остаются для невалидной MRZ. Из MRZ не получается отчество; латинское имя
   не заменяет кириллическое поле FRONT.
5. Подпись источника и переход к изображению выбирают кандидата, совпадающего
   с отображаемым значением. Порядок кандидатов по confidence не определяет
   источник кириллического поля. Ручной ввод и MRZ имеют отдельные подписи.
6. Ручной повтор имени, включая карточку официальной формы и выбранную
   альтернативу MRZ, перенаправляется к полной группе на FRONT. Другие поля
   сохраняются. У запроса собственный контекст кеша и билет актуальности.

Необязательная ошибка дополнительного чтения сохраняет уже прочитанные поля;
такой частичный результат не закрепляется в кеше. Поздние результаты проходят
прежние проверки run/case/image hash/rotation/version и не стирают ручной ввод.

## Модели и кеш

Модели создаются в дочернем процессе при первом запросе и повторно используются
между сторонами, клиентами и экземплярами сервиса. Запросы сериализованы.
Cyrillic predictor основной pipeline используется и для строк; второй экземпляр
его весов не создаётся. English predictor создаётся лениво один раз. Таймаут
и отмена останавливают дочерний процесс; следующий запуск создаёт его заново.

Кеш полного результата ограничен 16 записями, включая эквивалентные ключи после
автоматического определения стороны. Ключ включает case/image ID, SHA-256
байтов, поворот, выбранную версию, роль, настройки, штампы файлов моделей,
версию preprocessing и содержимое профилей. Возвращается независимая копия.
Изменение входа или профиля исключает старый результат; перед сохранением
проверяется, что вход не изменился во время обработки. Отдельный кеш inference
ограничен 64 результатами и также разделён по источнику и контексту.

Кеши находятся только в RAM. «Очистить рабочие данные» удаляет оба кеша,
сохраняя загруженные веса. Смена клиента не переносит распознанные значения.
Изменения Excel, ручные поля и подтверждения не кешируются.

## Сравнение backend

Проверены API и исходники именно установленного PaddleOCR/PaddleX. Отключены
дополнительные document orientation/unwarping/textline-модели; ориентация
обрабатывается геометрией карты, ограниченной проверкой 180° и ручным поворотом.
Лимит detector — 1600, без дополнительного уменьшения контрольных изображений.

* oneDNN/MKLDNN включён в отдельном эксперименте на PaddlePaddle 3.3.1:
  inference завершился ошибкой. В рабочей конфигурации он выключен.
* RapidOCR 3.8.1 + ONNX Runtime 1.23.2 испытаны в отдельной папке с проверенными
  SHA-256 моделей PP-OCRv5 mobile detector/Cyrillic/English. Нормализация
  detector приведена к конфигурации PP-OCRv5, классификатор строк не запускался,
  потоки ORT — 2/1. Наличие кыргызских букв в алфавите проверено.
  Импорт — 1,348 с, создание моделей — 0,433 с, обработка — 2,813 с / 2,097 с.
  Пять форм ФИО совпали, но этот вариант потерял орган/дату выдачи и проверку
  MRZ оборота. Он не принят из-за ухудшения критических реквизитов.
  RapidOCR/ORT не добавлены в зависимости или рабочую поставку.

Источники API и моделей:
[RapidOCR model list](https://rapidai.github.io/RapidOCRDocs/main/en/model_list/),
[официальный каталог моделей](https://github.com/RapidAI/RapidOCR/blob/main/python/rapidocr/default_models.yaml),
[PaddleOCR OCR pipeline](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/OCR.html).
